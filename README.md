# ai-sensei

**Give the answer. Then have the student teach it back to you.**

Photograph a problem you cannot solve (with your notes, if you have them) and a senpai
AI teaches it with a board. Formulas and working go on the board while the voice only
asks: "look at D here - it's positive, right? So?"
Right after being taught, the student is asked to **teach it back**: "now explain that
in your own words." Where the explanation stalls becomes a **gap in understanding** the
student themselves had not noticed, recorded in a "karte" and asked again after 1, 3
and 7 days.

- Audience: Japanese middle- and high-school students. Subjects: middle-school maths,
  high-school maths (I, A, II, B, III, C), middle-school English, high-school English
- Two languages, Japanese and English. **Overseas learners get overseas curricula**
  (Algebra 1 / Geometry / Algebra 2 / Precalculus / Calculus / Statistics)
  ([ADR 0005](docs/adr.md#adr-0005))
- Learning-science background: the self-explanation effect and the protégé effect
  (teachable agent)
- A [RevenueCat Shipaton 2026](https://shipaton.revenuecat.com/) submission (public and
  MIT from day one, to also enter the Next Gen Award)

[`docs/inception-deck.md`](docs/inception-deck.md) (the elevator pitch, the "won't do"
list, the trade-off sliders). Read it at the start of a sprint.

## Repository layout

```
apps/mobile/        Flutter (iOS first) + Riverpod 3 + livekit_client
apps/lp/            The landing page (Japanese and English, plain HTML/CSS). Served as Cloudflare Workers static assets
backend/api/        Cloudflare Workers + Hono — session creation / karte storage / billing webhook
backend/agent/      LiveKit Agents — the VAD/STT/LLM/TTS conversation pipeline plus board generation (the senpai character)
packages/contract/  Schemas and fixtures for the API, the karte and the board (`board.ts`) (both mobile and server validate the contract)
packages/curriculum/The curriculum map (plain JSON; middle/high-school maths and English, with overseas curricula kept separate)
packages/guardrail/ Pure functions: topic_id allow-list matching, board LaTeX command matching, spoken-maths normalization
prompts/            System prompts and few-shot examples (`<id>.<locale>.md`, a separate book per language. The board lesson is `senpai_board.*.md`)
docs/               Planning material, wireframes, ADRs
scripts/            Repository-wide verification scripts
```

The TypeScript side (`backend/`, `packages/`) is bundled with pnpm workspaces.
The Flutter side is self-contained in `apps/mobile`, and the two connect through
`packages/contract`'s schemas and fixtures.

### 1. Installing dependencies

```bash
git clone https://github.com/sarushili0430/ai-sensei.git
cd ai-sensei
pnpm install         # resolve the whole TypeScript side
```

### 2. Environment variables

**This repository is public. Never commit a real key.**
The templates are split **per deployment unit**.

```bash
cp backend/api/.dev.vars.example        backend/api/.dev.vars           # read by wrangler dev
cp backend/agent/.env.example           backend/agent/.env              # read by LiveKit Agents
cp apps/mobile/dart_defines.example.env apps/mobile/dart_defines.env    # --dart-define-from-file
```

| Template | Contents |
| --- | --- |
| `backend/api/.dev.vars.example` | LiveKit / Vision LLM / OneSignal / RevenueCat webhook / internal token |
| `backend/agent/.env.example` | LiveKit / conversation and karte LLMs / STT / TTS / internal token |
| `apps/mobile/dart_defines.example.env` | **Public values only** (the API URL, RevenueCat public keys, the OneSignal App ID, the Sentry DSN, the terms URLs, the support email) |

The billing dashboard setup and how the app meshes with it are in
[`docs/revenuecat.md`](docs/revenuecat.md).
A build with no keys disables billing entirely, so `flutter test` and CI pass without
any RevenueCat configuration.

`--dart-define` values are embedded in the build artifact and readable by
disassembly. **Do not put secrets on the mobile side.**

Production secrets are registered **per environment**, with
`wrangler secret put <NAME> --env <develop|production>` and in LiveKit's environment
settings ([`docs/deploy.md`](docs/deploy.md)).
To scan before committing:

```bash
pnpm run verify:secrets
```

### Pre-commit lint (lefthook)

git hooks are managed with [lefthook](https://lefthook.dev/) and install after one
`pnpm install` (`prepare` calls `lefthook install`).
The configuration is **split by what it inspects**, and the root `lefthook.yml` loads
each part.

| Config file | When it runs | Content |
| --- | --- | --- |
| `backend/lefthook.yml` | `.ts/.js/.json` staged under `backend/` | `biome ci <changed files>` |
| `apps/mobile/lefthook.yml` | `.dart/.yaml` staged under `apps/mobile/` | `flutter analyze` |

**pre-commit checks lint only.** typecheck, tests and builds are left to CI (waiting
tens of seconds on every commit pushes people towards disabling the hook).
The side you did not touch does not run: a backend-only commit needs no Flutter.

```bash
pnpm exec lefthook run pre-commit    # run it by hand
LEFTHOOK=0 git commit ...            # skip it temporarily
```

The `apps/mobile` side runs `flutter analyze`, which fails without the generated files
(`*.g.dart` / `*.freezed.dart`). Run `build_runner build` first after cloning.

Templates for the CI and deploy workflows are in [`docs/ci/`](docs/ci/README.md)
(a GitHub App cannot push to `.github/workflows/`, so the first copy is done by hand).

Opened in Claude Code on the web, `.claude/hooks/session-start.sh` runs at session
start and completes pnpm, the Flutter SDK (the `.fvmrc` version) and code generation,
so **lint and tests pass the moment the session opens**.

Biome handles both linting and formatting (there is no ESLint or Prettier).

The testing approach has two legs: (1) pure-function unit tests (guardrail matching,
spoken-maths normalization, the spaced-repetition scheduler, the hole/streak rollups,
contract fixture parsing) and (2) golden tests of the main screens.
There are 11 goldens across the main screens (3 of onboarding's 4, plus two states each
for home and review), generated in CI with **Linux rasterization as authoritative**
(`apps/mobile/test/golden/README.md`).
There are no E2E tests; manual checking on TestFlight is accepted instead.

Animations always respect the device's "reduce motion" setting
([ADR 0004](docs/adr.md#adr-0004)). Tests run through that path too, so adding a
looping animation and forgetting to route it means `pumpAndSettle` never returns and
the test hangs, which is how it gets noticed.

Dependency updates come from Renovate (`renovate.json`). Solo development, so they are
batched weekly with at most three PRs open at a time. Only Flutter SDK updates require
dashboard approval (so one does not arrive just before a submission).

## Deployment

`backend/api` runs on Cloudflare Workers as **two deployments, develop and production**.

| | develop | production |
| --- | --- | --- |
| Branch | `develop` | `main` |
| Worker | `ai-sensei-api-develop` | `ai-sensei-api-production` |
| D1 / R2 / KV | Dedicated resources | Dedicated resources |

Only the binding names (`DB`/`PHOTOS`/`METER`) are shared while the resources differ,
so the code is unaware of the environment. A push to `develop`/`main` makes GitHub
Actions run migrations, deploy, and check `/health`.

Creating resources, registering secrets and the API token's permissions are in
[`docs/deploy.md`](docs/deploy.md).
`apps/mobile` is distributed by Codemagic
([`docs/ci/codemagic.md`](docs/ci/codemagic.md)).

`backend/agent` (LiveKit Agents) is a **long-lived container** running on LiveKit
Cloud's agent hosting ([`docs/deploy-agent.md`](docs/deploy-agent.md)).
**The `Dockerfile` being at the repository root is deliberate** (the agent references
`packages/*` via `workspace:*`, and `lk` only reads a `Dockerfile` directly inside the
working directory; [the addendum to ADR 0002](docs/adr.md#adr-0002)).
The same image runs on any container host.

> **LiveKit projects are split per environment** (sharing one project would let a
> development agent pick up jobs from production rooms).

## Architecture

```
Flutter app ──HTTPS──▶ backend/api ──▶ create the LiveKit room + start the agent
     │                    │  Analyses the photo with a Vision LLM, deciding the unit and question policy (nothing counted yet)
     │                    │  The room opens when "start" is pressed = that is where the daily count happens
     │                    │  Storage: R2 (photos) / DB: D1 / metering: KV
     └──WebRTC────────▶ agent
                          VAD -> Japanese streaming STT -> the LLM (senpai persona)
                          streams {speech, board}. Each time a step completes, the board
                          is sent over LiveKit Text Streams and the speech goes to TTS
                          right after -> barge-in handled. At the end the karte is
                          generated from the transcript and POSTed to backend/api's
                          /v1/sessions/{id}/complete
                          -> OneSignal books +1 / +3 / +7-day return pushes
```

The senpai speaks only while teaching, and formulas, working and figures stack on the
board (never read aloud). The Flutter side stacks received steps line by line and never
erases earlier ones. The board elements' schema (LaTeX, plots, triangles, circles) lives
in `packages/contract/src/board.ts`, and mobile and the agent validate the same shape.

Question generation has two guardrails.
The prompt limits it to "what is in the notes photo ∩ the curriculum map's scope", and
the server matches the output's `topic_id` against the allow-list, regenerating what
falls outside. Board LaTeX is handled the same way: `packages/guardrail` matches
commands against an allow-list before sending, rejecting syntax that cannot be rendered.

## Two curricula (Japan / overseas)

`locale` runs end to end from photo analysis through the karte to notifications.
**It switches the taxonomy, not just the language** - showing an overseas learner
"Math II / coordinate geometry" does not match their textbook's contents page, so it
would not work as a hole's tag.

| | `ja` | `en` |
| --- | --- | --- |
| Curriculum | Math I-C (current guidelines) | Algebra 1 / Geometry / Algebra 2 / Precalculus / Calculus / Statistics |
| topic_id | `M2-ZUKEI-ENCHOKU` | `A2-COORD-CIRCLE` |
| Prompts | `prompts/*.ja.md` | `prompts/*.en.md` |
| STT / TTS | Japanese models | English models |
| Guardrails | Answer leaks, out-of-scope words, spoken maths in Japanese | The same in English |

The prefix of a hole's `topic_id` decides that hole's language. The review
notification and the review screen's one-liner follow it rather than the device's
language setting, so a hole explained in Japanese never arrives as an English
notification ([ADR 0005](docs/adr.md#adr-0005)).

## Design promises (to uphold while implementing)

1. **Teach, then have them teach it back.** The senpai teaches with a board and asks
   for an explanation on the spot.
2. **No scores.** Only streak days and filled holes are counted.
3. **Never shame a pass.** What could not be explained becomes a hole, which is value.
4. **Never nag.** Notifications and paywalls are written as the senpai's judgement: no
   numbers, no orders, no pressure.
