- **数字は本文より1段太く**(連続日数・埋めた穴のカウンター)

### 2-3. アイコン仕様

**アプリアイコン**

- マスター **1024 × 1024 px**、PNG、**アルファチャンネル無し・角丸を自前で付けない**(iOS側がマスクする)
- Xcode 15以降は 1024 の単一アセットから各サイズが生成される
- モチーフ候補: 後輩キャラの顔 / 吹き出し + マーカーの一筆。地を `blue #0EA5E9` にしてキャラを白抜きが第一候補
- **唯一の合格基準: 設定アプリ相当の小サイズ(29pt)で何のアプリか判別できること。** 細い線・文字を入れない
- ダークモード版・ティント版(iOS 18のアイコン外観)は**改善準備フェーズ**で追加

**UI内アイコン**

- グリッド **24 × 24 pt**、線幅 **2 pt**、端と角は **丸(round cap / round join)**。丸ゴシックと厚みボタンの角丸に合わせる
- サイズ段階は **16 / 20 / 24 / 32 pt** の4つだけ
- **線画で統一**。塗りはタブバーの選択状態のみ
- セットは**丸みのあるもの限定**(Lucide / Phosphor の Rounded 等)。角ばったセット(Material Symbols Sharp など)は世界観に反するため不可
- 色: 通常 `ink`、非活性・非選択 `muted`
- MVPに必要なアイコン14種: カメラ / マイク / 再撮影 / 戻る / 閉じる / 通知ベル / 設定歯車 / ホーム / カルテ / 復元 / ゴミ箱 / 外部リンク / チェック / 炎(連続日数)

**キャラの表情差分**

- 5枚: 通常 / 聞いてる / なるほど / うーん / 祝福
- MVPは **SVG or PNG の差分 + Flutterの暗黙アニメーション**。Riveのステートマシン化は改善準備フェーズ

### 2-4. スクリーンサイズ仕様

**縦向き固定**(横向き非対応)。学習アプリで横持ちの必然性がなく、会話画面のレイアウトが破綻するため。

| 区分         | 論理解像度(pt)    | 代表機種            | 設計上の扱い                                       |
| ------------ | ----------------- | ------------------- | -------------------------------------------------- |
| **Compact**  | 375 × 667         | iPhone SE (2nd/3rd) | **最小保証**。ここが通れば全機種通る               |
| **Standard** | 390–393 × 844–852 | iPhone 12〜16 標準  | **基準デバイス**。ストアスクショもここ(1179×2556) |
| **Large**    | 428–440 × 926–956 | Pro Max 系          | 余白が増えるだけ。中央寄せで吸収                   |

**レイアウト規則**

- **Compact(SE)での検証を必須にする。** 最も危ないのは会話画面(03): 直径118ptのマイクボタン + 吹き出し + パスボタンが 667pt に収まらない。Compactではマイクを **96pt** に縮める
- セーフエリア: 下部ホームインジケータ **34pt** を必ず避ける。祝福画面の紙吹雪だけはセーフエリア外まで描いてよい
- **固定サイズ**: マイクボタン・キャラ・タブバー / **可変**: テキスト・カード・余白
- 縦が詰まったら **余白を削る → 要素を削る** の順。要素を削る場合、会話画面で最初に落とすのは進捗表示
- 最小タップ領域 **44 × 44 pt**
- Dynamic Type は **「大」まで対応**。マーカー表現(下線グラデーション)が行高の変化で崩れないことを確認
- 横スクロールは作らない。単元チップだけは折り返しではなく横スクロールを許可

**golden test はこの3区分で撮る**(Compact / Standard / Large)。

### 2-5. コンポーネント

| コンポーネント       | 仕様                                                                 |
| -------------------- | -------------------------------------------------------------------- |
| 厚みボタン(主)       | 角丸16、`blue`地、影 `0 5 0 blueDark`、押下で5pt沈む + 弱ハプティクス |
| 厚みボタン(副)       | 白地、`muted`文字、影 `0 4 0 line`、枠2pt                            |

| チップ               | 角丸99、`pinkLight`/`orangeLight` 地に濃色文字                       |
| カルテカード         | 白地、枠2pt `line`、角丸16                                           |

### Q-3. 音声とノート写真の保存方針 【B-02のD1スキーマに直結・回答が早くほしい】

ターゲットが未成年で写真と音声を扱うため、App Store審査で必ず問われます。

- **ノート写真をR2に保存しますか、解析後に破棄しますか。** 破棄でも要件は満たせます(カルテに写真は要らない)。破棄なら P-01/P-02 が大幅に軽くなります
- **音声そのものを保存しますか、transcriptだけにしますか。** transcriptのみを推奨します。プライバシー・ストレージ・審査のすべてで有利です
- 匿名デバイスID方式なので「アカウント削除」要件は回避できますが、**データ削除導線**(設定画面から履歴を消す)は M-03 に含める前提でよいですか
- **プライバシーポリシー・利用規約は私が草案を書きますか**、それとも用意がありますか

### Q-4. 検証用のノート写真サンプル 【C-07の前提】

ガードレールの意地悪テストとVision LLMの手書き認識精度検証に、**高校数学ノートの写真が5〜10枚**ほしいです。手書き・板書撮影・問題集撮影など撮り方のばらつきがあると精度がわかります。無ければ手書きサンプルをこちらで作りますが、実物のほうが精度がはっきりします。

### Q-5. Go/No-Goの合格基準 【S-07】

叩き台:

- 発話終了 → 後輩の応答開始まで **1.5秒以内**(Wi-Fi/4G前提)
- 数式を含む発話の**意味が通る率 8割以上**(語の完全一致ではなく、Claudeが文脈補正した後の解釈が正しいか)
- 5分の会話で**セッション断 0回**

この基準でよいですか。

### Q-7. キャラ設計

後輩キャラの**名前・一人称・口調・性別表現**を決めたいです。design_direction のSVG(青い丸顔)を叩き台に、表情差分5枚をこちらで作れます。「最大の報酬はキャラの表情」が設計の核なので早めに固めたいです。ジェンダーを特定しない造形にしておくとターゲットを狭めずに済みます。

### Q-8. 声を出せない環境向けのテキスト入力

### Q-11. デフォルトブランチ

### Q-13. 「穴」という言葉の強度 【wireframe末尾の未決論点】

wireframeが「刺さるが強すぎる可能性(代案: モヤ、ハテナ)」と提起しています。**今決めたい**です。「穴」はUI文言だけでなく、カルテJSONのキー(`holes`)・D1のテーブル名・「埋めた穴」カウンター・通知文まで貫通しており、後から変えると広範囲の改名になります。

推奨は **「穴」のまま**。「埋めた穴の数」がこのアプリ固有のスコアとして成立するのは「穴」の具体性があってこそで、「モヤを3つ晴らした」では手触りが弱い。また「穴」は**埋まる**ので可逆・前向きです。

ただし**通知文だけは「穴」に言及しない**のを提案します。「3日前の穴、まだ埋まってません」は不採用リストの「罪悪感で煽る通知文」に近づきます。wireframeの「いまなら説明できますか?」の形が正解です。

### Q-14. タブバーの「カルテ」の遷移先

未設計です。**06「復習」画面をカルテタブの中身にする**(無料は当日のカルテ、Premiumは履歴+穴一覧を出し分け)のが画面を増やさず済むので推奨です。

### Q-15. 会話画面に「Q1/3」の進捗表示を残すか

wireframeは録音式時代なので「Q1/3」「1問60秒」ですが、会話型では「5分・2〜3問」に変わります。**残り時間バーのみ**を推奨します。会話は問数で区切れるものではなく、無理に区切ると「試験官UIにしない」という原則に反します。

### Q-16. #BuildInPublic($30k)は併願しますか 【private方針との関係】

privateで進める方針に伴い Next Gen は取り下げましたが、**#BuildInPublic はリポジトリの公開可否とは別の賞**です。要件は「#Shipatonタグで開発過程をXに週次投稿」で、フォロワー数は不問。**ソースを公開しなくても、進捗・スクショ・学びを投稿すれば併願できます。**

賞金は$30kで併願スタック中の最高額です。「publicの賞もskip」がこれも含む意図でしたら外しますが、**リポジトリ非公開のまま続行できるので残すことを推奨します。** どちらにしますか。
