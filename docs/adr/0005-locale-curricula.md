# ADR 0005: 英語対応は「訳す」ではなく、課程とプロンプトをロケールごとに別で持つ

- ステータス: 承認
- 日付: 2026-08-07
- 関連: [`handoff_to_opus.md`](../handoff_to_opus.md) §3-7 /
  [`0003-voice-provider.md`](0003-voice-provider.md) /
  [`packages/curriculum/README.md`](../../packages/curriculum/README.md)

## 背景

英語対応はもともと「審査員が触れる」ための最小対応として入っていて、実体は
2か所しかなかった。

1. 画面の文言(`AppStrings` の日英2ロケール)
2. agent が日本語のプロンプトの末尾に
   `Respond in English. Keep the same persona and the same rules.` を足す

これで英語**は**話す。ただし後輩が聞いてくる中身は、最後まで日本の課程のままだった。

- 写真解析に渡すカリキュラムマップは `数学I`〜`数学C` の52トピックだけ。
  Algebra 2 のノートを撮ると、いちばん近い日本の単元に丸められる。
- チップUIに出る科目名は「数学II / 図形と方程式」。海外の高校生には
  **自分が今なにを勉強しているのかが書かれていない**。
- カルテの穴も、通知も、同じ単元名で残る。
- ガードレール(答えの漏れ・範囲外の語・質問の形)はすべて日本語の正規表現。
  `The answer is 2.` は素通りしていた。

つまり英語対応は、**言語の問題ではなく分類の問題**だった。

## 決定

### 1. カリキュラムはロケールごとに別のマップを持つ(訳さない)

`数学I` を "Math I" と訳したものは、どこの国のカリキュラムでもない。
海外向けは、国際的にいちばん通りのいい並びで**別に作る**。

| ロケール | ファイル | 課程 |
| --- | --- | --- |
| `ja` | `data/curriculum.v0.json` | 数学I / A / II / B / III / C(新課程・52トピック) |
| `en` | `data/curriculum.intl.v0.json` | Algebra 1 / Geometry / Algebra 2 / Precalculus / Calculus / Statistics(57トピック) |

対応表は作らない。「三角比 ↔ Right Triangle Trigonometry」のような対応は
だいたい合っていてもどこかで必ずずれるし、ずれた場所は**両方の課程の
どちらでもない単元**になる。それぞれの課程の中で閉じているほうが、
質問の材料としても穴のタグとしても正しい。

### 2. ロケールは topic_id の接頭辞で判る

接頭辞はロケールをまたいで重複させない(`M1`〜`MC` が日本、
`A1`/`GE`/`A2`/`PC`/`CL`/`ST` が海外)。

これで、**穴に付いた topic_id からその穴の言語が決まる**。カルテの文言は
その課程の言語で書かれているので、通知文と復習画面の一行は端末の言語設定では
なくこちらに従う。セッションのロケールをDBに持つ必要がなくなり
(マイグレーションも要らない)、「日本語で説明した穴が英語の通知で届く」も
起こらない。

### 3. プロンプトは言語ごとに別本にする

`prompts/<id>.<locale>.md`。日本語の本文に「英語で答えて」を足す作りをやめる。

足す作りだと、ペルソナ(後輩)も禁止事項も日本語のまま英語で薄く言い直される。
few-shot は日本語の例文のままなので、**文体の見本がない状態**で英語を喋ることになり、
試験官の口調に寄りやすい。プロンプトは仕様書なので、言語ごとに書く。

差し込む定型句(`(なし)` / `(none)`)とロール名(`後輩:` / `Kohai:`)も
本文と同じ言語に揃える。日本語が1行混ざると、そこだけ日本語で返ってくる。

### 4. ガードレールも言語ごとに書く

答えの漏れ・質問の形・範囲外の語を、日英それぞれの語彙で持つ。
**範囲外の語は課程ごとに違う**のが要点で、たとえばロピタルの定理は日本の
高校では範囲外だが AP Calculus では扱う。一本のリストにすると、英語の
セッションで教科書どおりの話題まで弾いてしまう。

### 5. 端末の言語の解決は「日本語を望んだ人にだけ日本語」

Flutter の既定は「一致しなければ `supportedLocales` の先頭」なので、
何もしないとスペイン語の端末に日本語が出る。`localeListResolutionCallback` で
日本語を望んだ端末にだけ日本語を出し、それ以外は英語に寄せる。

### 6. ただし、設定でアプリだけ言語を選べる

端末の言語に従うのは**既定**であって、決めつけではない。設定画面に
「端末に合わせる / 日本語 / English」を置き、選ばれていればそちらを
`MaterialApp.locale` に渡す(選択は `SharedPreferences` に残す)。

端末を日本語のまま英語で説明したい人(逆も)がいるのが理由。端末の言語を
変えれば済む話に見えるが、それは**他のアプリまで全部変わる**操作なので、
このアプリのために払わせる代償としては大きすぎる。

ここで選んだ言語は画面の文言だけでは終わらない。セッションを作るときに送る
`locale` がこれになるので、後輩の話す言葉・課程・ガードレール・音声まで
まとめて切り替わる(それが §1〜§4 の設計そのもの)。逆に、**すでに書かれた
カルテと穴は元の言語のまま**残る —— 穴の言語は topic_id が決めていて(§2)、
アプリの設定では動かない。

## 結果

- 英語のセッションは、写真解析 → 許可トピック → 会話 → カルテ → 通知まで、
  ぜんぶ海外向けの課程で揃う。混ざったら落ちるように、各層のテストで見る。
- カリキュラムを足すときの作業がロケールぶんに増える。整合性検査
  (`checkIntegrity`)を全ロケール横断にして、課程をまたいだ前提参照と
  ID重複をCIで落とす。
- STT/TTSは以前から `locale` で選び分けている([ADR 0003](0003-voice-provider.md))。
  ここは変えていない。

## 代替案

- **日本の課程を英訳する。** 実装はいちばん小さいが、"Math II" は誰の課程でもない。
  海外のユーザーにとって、自分の教科書の目次と一致しない分類は
  「穴のタグ」として機能しない(復習の通知が他人事になる)。
- **ロケールをDBのセッション行に持つ。** マイグレーションが要るうえ、
  穴は復習で別のセッションから参照されるので、結局「その穴の言語」を
  別に決めることになる。topic_id から引けば一意に決まる。
- **1本のカリキュラムに両方の課程を入れる。** 写真解析に渡す一覧が2倍になり、
  解析器が課程をまたいで選び始める(日本語のノートに `A1-...` が付く)。
