# AIアーキテクチャ検討 v1 — 「板書 + 発言」を生成するAIは何でできているべきか

作成日: 2026-08-23

`backend/agent/src/lesson.ts` / `lesson-loop.ts`・`packages/contract/src/board.ts`・`prompts/senpai_board.*.md`

この文書は「黒板(板書)と先生の発言をまとめて出力するAI — いま実現しようとしているAIそのもの — を
**0から設計し直すならどういうAIアーキテクチャにするか**」への答え。オーケストレーションを続けるのか、
ファインチューンするのか、事前学習まで遡るのか、を含めて検討し、**移行の条件を数値で決めておく**
(判断を先送りしないのは計画書 §3-4 と同じ流儀)。

## 0. 結論(先出し)

| # | 結論 |
| --- | --- |
| 1 | **0から設計しても、ほぼ現行の形に収束する**: 汎用フロンティアLLMを `LessonLlm` の狭い口の奥に置き、契約(`board.ts`)・ガードレール・修復・配送を**コードで**持つオーケストレーション。理由は §2(保証はweightsでは作れない) |

## 1. 要件の分解 — このAIに必要な6つの性質

「板書と発言をまとめて出す」を分解すると、要求は6つ。**アーキテクチャの答えは、
どの性質をどの層が守るかで決まる。**

| # | 性質 | 要求 | いまの守り方 |
| --- | --- | --- | --- |
| G1 | 描画可能性 | 出した板書が端末で必ず描ける | スキーマ + 三段ガードレール(式テンプレ / コマンド照合 / KaTeXパース)+ 修復ループ |
| G2 | 範囲と順序 | 許可トピック内・先に答えを埋めない・答案を流し込まない | topic_id照合・手順数/文字数上限・`awaits_student` で止まる往復 |
| G3 | 原価契約 | 声は問いかけと接続だけ(TTS原価が価格設計の柱) | `speech` ≤120字を**スキーマで**強制 |
| G4 | レイテンシ | 最初の手順まで数秒・以降ストリーム | ストリーミングJSON逐次パース + prompt cache + thinking無効 + プリレンダ音声 + 先読み合成 |
| G5 | 数学の正しさ | 間違いを教えたら製品として終わり。**上限のない要求** | フロンティアモデルの素の能力(+誤読の保険としての教え返し) |
| G6 | 授業の質 | 節目で問いかける・長い式は割る・板書だけで読み返せる | 43KBのプロンプト + few-shot + 8/16ゲートの目視 |

G1〜G4は**契約で閉じている**(有限の要求)。G5だけ性質が違う — どんなモデルでも確率でしか
満たせず、その確率を1に近づける手段が問題になる。**アーキテクチャ選定の本体はG5をどう扱うか**で、
G1〜G4は実はもう解けている。

## 2. 中心の整理 — 「構造」と「知能」を分ける

この製品のAIは1個のモデルではない。**構造(G1〜G4の保証)と知能(G5〜G6)を別の層に置いた
複合体**で、境界は `LessonLlm`(`lesson.ts`)の1インターフェースにある。

```
知能(差し替え可能)         構造(差し替えない・ここが製品)
┌───────────────────┐   ┌─────────────────────────────────────────┐
│ LessonLlm.stream()  │→ │ 逐次パース → boardStepSchema → guardrail │
│  いまはフロンティア  │   │ → 修復(再生成) → 封筒/seq → LiveKit      │
│  (FTモデルでも可)   │   │ → 検証済みの手順だけTTSへ                │
└───────────────────┘   └─────────────────────────────────────────┘
```

この分割から出る帰結が3つあり、**選択肢の大半はここで決着する**。

1. **保証はweightsでは作れない。** どれだけ調教しても「LaTeXホワイトリスト外を出さない確率」は
   1にならない。だからスキーマ検証・照合・修復の層は、どのモデルを中に置いても**消えない**。
   「ファインチューンすればガードレールが要らなくなる」は成立しない — 発火頻度が下がるだけ。
2. **text-firstの決定的な利点は、検証が生成と発話の間に入ること。** いまの授業は
   「手順が閉じる → 検証 → 送信 → 直後にTTS」(`runBoardLesson`)。**しゃべる前に**落とせる。
   音声ネイティブ(E2E)のモデルは先に声が出るので、板書が検証に落ちた時にはもう言ってしまっている。
   取り消せない失敗になる。
3. **共同生成は正しい。** speechは板書を指差す(「ここ、Dを見てほしいんだけど」)。boardとspeechを
   別モデルに分業させると、この指差しがズレる。分業を入れるなら**生成側ではなく検証側**(§7-2)。
   `figure` が既にこの形をしている — LLMは関係の宣言だけを書き、座標はコードが解く。

## 4. 各論

### 4-1. A(オーケストレーション)— 0から見直しても、ここに戻る

0からの設計を要求から順にやり直すと:

1. 板書は構造(スキーマ)を持たざるを得ない(端末で描く・検証する・後から読み返す)
2. 構造化された板書と自由な発話を**1つの文脈**で出す必要がある(指差しの同期)→ 共同生成のストリーミングJSON
3. しゃべる前に検証したい → text-first(声はあとからTTSで付ける)
4. 数学の正しさと日本語の授業力は、当面フロンティアモデルからしか出ない → 借りる
5. モデルは製品の寿命の間に何度も替わる → 狭いインターフェースの奥に置く

…と、**現行の形が導出される**。これは「既にあるから維持」ではなく、要求からの再導出でも
同じ答えになるという確認。計画書 §3-2〜3-6 の設計判断(手順単位の同期・プリミティブ固定・
三段ガードレール)は、モデル選択より寿命が長い**製品そのもの**で、どの案を選んでも持ち越される。

現行の弱点も明確で、
(a) スキーマ構文違反 → 修復1回ぶんの待ち(その間は沈黙)、
(b) G5をモデルの素の能力だけに預けている、
(c) セッションが学習に使える形で残っていない。
§7の3手はこの3つに1対1で対応する。

### 4-2. B(E2E音声一本化)— 授業フェーズでは成立しない

「STT→LLM→TTSを1つの音声ネイティブモデルに畳めば、レイテンシも構成も軽くなるのでは」への答え。

- **検証の位置が逆になる。** §2-2 の通り。板書が三段ガードレールに落ちたとき、声はもう出ている。
  「言ったが書けなかった」授業は成立しない。
- **原価契約が壊れる。** 声の短さ(≤120字)は**スキーマの上限**で守っている(`boardSpeechMaxLength`)。
  音声ネイティブモデルの発話量はプロンプトのお願いに戻ってしまい、TTS原価を柱にした価格設計
  (計画書 §6-1)の土台が消える。しかも音声トークン課金は文字課金より高い。
- **傍証が手元にある。** Gemini Live を読み上げ専用に使う経路(`gemini-live-tts.ts`)ですら
  「逐語で読む確度が低い。要約・相槌・返答が起きうる」(agent README)。対話に後訓練された
  モデルに形式の厳守をさせるのは訓練の逆方向 — 板書という**形式そのもの**を任せるのはさらに逆方向。
- 残る魅力は教え返しフェーズの応答速度と自然さ。あちらは出力が非構造(会話)なので上の議論が
  当たらない。**音声トークン単価が下がったタイミングで、フェーズ2限定の実験候補**として残す。

### 4-3. C(ファインチューニング)— 何が良くなり、何が良くならないか

**良くなるもの**: 形式追従(スキーマ準拠率・語彙の逸脱率)、文体(先輩の声)、方針の焼き込み
(43KBの指示の大半をweightsに移す → プロンプト縮小でTTFTと原価が下がる)、そして単価
(小型モデルで回る)。

**良くならないもの**: **数学の正しさ(G5)。** 数千件のSFTで身につくのは書き方であって数学ではない。
小型モデルをFTすると「**形式は完璧、数学が間違い**」という、この製品で最悪の組み合わせが出やすくなる。
確信に満ちた先輩の声で間違いを教え、それを1/3/7日の復習で強化する — Dの却下理由と同じ壊れ方を、
安く実現してしまう。

だからFTを入れるときの形は**カスケード(C3)一択**:

```
小型FTモデルが生成 → スキーマ + ガードレール + 数値検証(§7-2)
   → 通った手順だけ配送
   → 落ちた手順はフロンティアモデルで修復(いまのrepair経路そのまま)
```

修復経路は既に `LessonLlm` 単位で書いてある(`lesson.ts` の `repairStep`)ので、
**生成と修復に別のモデルを渡すだけ**でこの形になる。アーキテクチャの変更ではなく配線の変更。

**教材はどう作るか** — 2系統:

| 系統 | 中身 | 前提 |
| --- | --- | --- |
| 実運用蒸留 | 検証を通り、かつ結果が良かった(教え返し成立・修復なし・離脱なし)レッスンを教材化 | §7-3 の記録形式 |
| 合成蒸留 | `packages/curriculum` の topic_id 全域を覆う問題バンクを作り、現行の板書LLMでオフライン一括生成 → 同じガードレール + eval で選別 | ユーザー数に依存しない。一括なら Batch API(50%引き)が使える |

**先に確認する制約が2つ**(どちらも要調査。ここでは断定しない):

- **利用規約**: フロンティアモデルの出力で自前モデルを学習することは、ベンダー規約の
  「競合モデルの学習禁止」条項に抵触しうる。蒸留に踏み出す前にその時点の規約を確認する
- **学習利用の告知とデータの線引き**: §7-3。未成年ユーザーの製品で「学習に使う」は、
  規約への明示と最小化(先輩の出力と導出要約だけ。生徒の音声・写真の原本は使わない)が前提

**FT先の候補**(2026-08時点の理解。着手時に再調査):

| 経路 | 例 | 特徴 |
| --- | --- | --- |
| ホスト型チューニング | Vertex AI の supervised tuning(Gemini Flash系)/ OpenAI の mini系FT | サービング運用なし。ベンダーが1社増える |
| オープンウェイト | Qwen3 / Gemma 3 の 8〜32B + LoRA | 単価最小・支配権最大。サービング(夜のスパイクに合わせたウォームプール)がソロに重い |

Anthropic はセルフサーブのFTを提供していない(2026-08時点)ので、C1はベンダー追加を意味する。
STT/TTSで既に複数社構成(ADR 0008)なので致命ではないが、数式の書き方の癖はモデルごとに違うので、
移行判定は必ず §7-3 の eval を通す。

### 4-4. D(0から事前学習)— 却下の算術

- 高校数学全域で間違えない能力は**事前学習のスケール**から来る。自前で得るには数百B〜数Tトークン級の
  コーパスと$1M級以上の計算資源が要り、それでもフロンティアに数学で劣るモデルしか得られない
- 学習が終わる頃には要求(スキーマ・課程・教え方)のほうが変わっている。このモデルに要る性質のうち
  **独自なのは形式と文体だけ**で、それはSFT/LoRAで足りる — 事前学習を正当化する独自要素が無い
- 差別化(moat)はweightsではなく、**契約 + ガードレール + 配送の機構と、結果ラベル付きの授業データ**に
  置く。前者は既にあり、後者は §7-3 で作る。この2つはモデルが何度替わっても生き残る

### 4-5. E(ソルバ主導)— 生成には使えないが、検証には使える

「CAS(数式処理系)で解を作り、LLMには語らせるだけにすれば間違いは消えるのでは」への答え。

- **生成に使えない理由**: 適用範囲が非対称。文章題・証明・図形・場合の数・英語には CAS の解が無い。
  生成側に置くと「解ける単元しか教えられないAI」になる。さらに授業は生徒の答えを受けて曲がる
  (`lesson-loop.ts` の往復)ので、事前に解を固定するパイプラインは往復に弱い
- **検証に使える理由**: 検証は部分的でも価値が出る。「検算できる手順だけ検算し、できない手順は素通し」で
  G5の実効確率が上がる。**生成には100%の網羅が要るが、検証は10%の網羅でも10%ぶん事故が減る**
- 具体化が §7-2(ガードレール第4層)

## 6. ボトルネックの現実 — FTで解きたくなる問題は、FTでは解けない

- **レイテンシの支配項はTTS。** 実測(agent README)で Gemini TTS 2.5 flash のTTFB中央値は3.7秒。
  板書LLM側は prompt cache + thinking無効 + 先読み(`speech-prefetch.ts`)で既に絞ってあり、
  モデルを小さくしても沈黙はTTS側に残る。**レイテンシ目的のFTは割に合わない**
- **原価の主柱もTTS + STT(計画書 §6-1)。** LLMは合計の半分弱。FTの効きは「効く。ただし半分にだけ」
- 先に効く打ち手は、キャッシュヒット率の維持(`llm_cache_hit_ratio`)・systemTail方式の徹底・
  非同期物(親レポートなど)の Batch API 化

## 7. 0から設計して現行と変える3点(= 次の一手)

### 7-1. 構造化出力のスパイク(1日)

`packages/contract` は既に zod → JSON Schema を吐いている(`generate-json-schema.ts`)。
これを構造化出力(constrained decoding / strict tool)に渡せば、**構文違反の修復ループがほぼ消える**。
確認することは2つだけ:
(a) ストリーミングと両立するか(手順単位の逐次配送は譲れない)
(b) TTFTが伸びないか。

`LessonLlm` の実装を1つ足して `voice_metrics` で比べる。ダメなら捨てる — 現行の逐次パーサは
そのまま残す。なお `superRefine` や正規表現などJSON Schemaに載らない不変条件は、
どのみちコード側の検証に残る(README「JSON Schema に現れない不変条件」と同じ整理)。

### 7-2. ガードレール第4層: 数値検証(G5への唯一の構造的な手)

`latex` 手順の `A = B` 形を機械で検算する。`plot.fn` で既にやっている
「文法を閉じて自前で評価する」の哲学を、式の**中身**へ延長する:

- `x^2-3x+2=(x-1)(x-2)` → xに乱択した数点を代入して両辺一致を見る
- `D = 9 - 8 = 1` → 定数式は両辺をそのまま評価
- 未知の文字が残る式・不等式・文章 → **素通し**(検証の網羅は部分的でよい・§4-5)

落ちたら既存の修復経路(`repairStep`)へ「計算が合いません」を渡すだけ。
**しゃべる前に**数学の誤りを1件でも落とせる層は、中のモデルを何に替えても価値が残る。
C3カスケードの前提装置でもある。

### 7-3. lessoneval とデータフライホイール(FTの選択権を無料で買っておく)

`docs/figeval`(39枚の実測で語彙と上限を決めた)と同じことを授業全体でやる:

| 部品 | 中身 |
| --- | --- |
| 入力 | topic_id を覆う問題バンク(著作権上、教科書の転載ではなく自作 / 言い換えで持つ) |
| 自動判定 | スキーマ合格率・ガードレール棄却率(層別)・修復率・式幅(>340pt)・speech長分布・「先に答えを埋めない」の順序検査・パス数・トークン費・TTFT |
| 審査 | 強いモデルによる採点(板書だけで追えるか・問いかけは節目か)+ 数学の抜き取り検算 |
| 本番の突き合わせ | モデル / プロンプト版ごとの教え返し成立(`speech_ratio`)・`lesson_empty`・穴の質 |

これが無いと、モデル差し替えも構造化出力もFTも**全部「耳で確かめる」しかなく**、
8/16ゲートのような目視を毎回やることになる。**evalはアーキテクチャ選択の前提装置。**

あわせて、セッションを**蒸留可能な形**で残す:

| 残す | 残さない |
| --- | --- |
| 写真解析の**要約**・許可トピック・レッスンJSON(実際に配送した手順)・検証 / 修復イベント・結果ラベル(教え返し成立・`ended_reason`・穴) | 生徒の音声・写真の原本(計画書 §4-1 の「解析後破棄」方針と整合)・個人を特定する情報 |

未成年の製品なので、学習利用は規約への明示と最小化を先に済ませる。
**残していないデータは、後からはどうやっても作れない。** フライホイールの整備だけは、
FTをやらない未来でも無駄にならない(evalの教材と原価分析にそのまま使える)。

## 8. 推奨アーキテクチャ(まとめ)

```
いま(〜9/5)            A1のまま + §7の3点(eval → 数値検証 → 構造化出力スパイク)
ローンチ後              フライホイールでデータと実測を貯める(W3テレメトリと同じ動き)
T1〜T4成立(目安200/日)  C1: 合成 + 実運用蒸留で小型モデルをSFT → C3カスケードへ配線替え
さらに規模(1,000/日〜)   C2: オープンウェイトLoRA + 自前サービングを再評価
ずっとやらない           D(事前学習)・授業フェーズのE2E音声一本化
```

一言でいえば: **知能は借りて、構造は自前で持つ。** 借り先はいつでも替えられるように
狭い口(`LessonLlm`)の奥に置き、替える判断ができるように eval とデータを先に持つ。
weightsはあとから買えるが、失ったデータと「検証が発話より先」という位置は買い戻せない。
